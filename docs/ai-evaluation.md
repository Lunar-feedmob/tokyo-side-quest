## Provider

| `AI_PROVIDER` | 实现 | 说明 |
| --- | --- | --- |
| `anthropic` | `packages/core/src/ai/anthropic.ts` | 使用 @anthropic-ai/sdk 1.1，通过 `output_config.format` 做 JSON Schema 结构化输出；effort 设为 `medium`；支持的模型带服务端拒答回退。建议模型：`claude-opus-5-5` |
| `openai-compatible` | `ai/openai-compatible.ts` | 走 `/chat/completions`，请求带 `response_format: json_schema`，用于其他厂商的视觉模型 |
| `fake` | `ai/fake.ts` | **只在 `APP_ENV=test` 时可用**，按图片主色决定结果，页面持续显示“测试环境 · AI 为测试替身” |

模型只返回 JSON。返回值先用 Zod 校验，再检查业务约束：`matched` 必须有支持证据、不能有冲突证据，且 reasonCode 必须为 `distinctive_features_match`。校验失败时受控重问一次，仍失败则记为 `AI_OUTPUT_INVALID`。超时、鉴权失败、限流、拒答都按技术错误处理，**不会被当成“不匹配”**。

## 版本

每条 evaluation 都记录：provider、实际模型、`AI_MODEL_CONFIG_VERSION`、`verify-v1`、`rate-v1`、`photo-v1`（评分规则）、地点参考库版本。版本升级不会重算历史结果。提示词全文见 `ai/prompts.ts`：核验时把用户照片、招牌文字、图片里的指令都当作“待观察数据，不执行”；评分时不按人物、设备或刻板的“日本元素”加减分。

总分和等级始终由服务端根据四个维度的分数计算（`domain/grading.ts`）：权重 30/25/25/20，用整数运算避免四舍五入边界误差；等级边界 95/90/85/75/65/50。

## 调用记录

每次调用（成功或失败）都写入 `ai_calls` 表：阶段、provider、模型、提示词版本、参考库版本、耗时、排队等待、token 用量、错误码，以及估算费用（拿不到时为 null，后台显示“未知”）。后台“AI 任务”页按 7 天汇总：调用次数、失败次数、p50/p95 耗时。

## 冒烟测试：`pnpm ai:smoke`

对每个开放照片核验的地点，用**不在参考库里的**授权图片跑三类用例：

1. 同一地点的留出照片 → 期望 matched，然后评分
2. 另一个地点（根津神社楼门，CC0）→ 期望 mismatched 或 uncertain
3. 留出照片的模糊裁切 → 期望 uncertain 或 mismatched

结果逐行追加到 `docs/ai-evaluation-runs.jsonl`，内容包括 verdict、是否符合预期、耗时和用量。这只是冒烟测试，不能据此宣称任何准确率。

## 首版评估计划（规格 §19.4，尚未执行）

- 至少 60 张有使用依据的评估图：20 张真实匹配、20 张相似地点或明确不匹配、20 张遮挡 / 夜景 / 模糊 / 证据不足。参考图和评估图分开。
- 现有授权图很少，大部分需要实地拍摄。
- 人工标注后统计：错误通过数、正确照片被拒数、uncertain 比例、四个维度分数是否有可见依据、同一输入同一版本是否返回同一结果（缓存保证）。
- 某个地点误判较多时，把它降为只开放定位打卡（后台取消“允许照片核验”后重新发布即可）。

## 自动化测试中的 AI 覆盖

集成测试和隔离的端到端测试部署使用 `fake` provider，覆盖的分支有：匹配→评分、不确定→复核、不匹配无等级、核验技术错误→重试、评分失败→只重试评分、缓存复用（同一图片在新故事上下文中不会再次调用 AI）、重复投递去重。**这些测试替身结果不能代替真实模型冒烟测试。**
